# Platform architecture

Product decisions live in `platform-vision`; this skill covers how to build it.

## Stack

| Layer | Choice |
|---|---|
| Frontend | React + TypeScript SPA (Vite), TanStack Router, TanStack Query, HeroUI v3 + Tailwind v4, lucide-react |
| Notebook display | markdown-it + KaTeX + Shiki (same as `site/scripts/notebook.mjs`), DOMPurify on display, Plotly lazy-loaded |
| Visualizations | The 13 React visualizers + kit from `site/src/viz/`, reused as-is |
| API | Hono on Cloudflare Workers; Zod validation; typed client (Hono RPC) |
| Database | Cloudflare D1 (SQLite) through Drizzle ORM; migrations in git |
| Real-time | Durable Objects (SQLite-backed, WebSocket Hibernation) |
| Python | Pyodide in a Web Worker (see `platform-live-coding`) |
| AI | Provider-agnostic layer (see `platform-ai`) |
| Email (phase 5) | Resend (free: 3,000 a month, 100 a day) |
| Tooling | Wrangler + `@cloudflare/vite-plugin`, Vitest (`@cloudflare/vitest-pool-workers`), Playwright, Biome, GitHub Actions |

- One Worker serves both the SPA's static assets and `/api/*`. Same origin means no CORS and
  simple cookies.
- Language: TypeScript everywhere.
- Repo layout (`goldenFlori/lab-platform`, private):
  - `src/web` (React SPA), with file-based routes in `src/web/routes`
  - `src/api` (Hono Worker), with `src/api/db` (Drizzle schema and access)
  - `migrations/` (D1, generated by drizzle-kit)
  - `test/` (Vitest inside workerd) and `e2e/` (Playwright)
  - `src/shared` (Zod schemas and types for the API and the app; the app imports only types)
  - Planned: `src/notebook` (converter), `src/viz` (visualizers).
- Version pins with a reason:
  - **Vitest 4.x:** `@cloudflare/vitest-pool-workers` 0.22 does not support Vitest 5 yet.
  - **TypeScript 5.9:** TypeScript 7 (the native compiler) is out; upgrade deliberately, not in
    passing.
  - **Drizzle 0.45 / drizzle-kit 0.31:** 1.0 is still a release candidate (checked 2026-10-06). It
    moves each migration into its own folder, which needs `migrations_pattern` in
    `wrangler.jsonc`, so upgrade deliberately.
  - **`compatibility_date`:** never newer than the test runtime's workerd supports
    (2026-08-22 today), otherwise the tests fail to start.

## Free-tier limits

Verified 2026-10-06. Re-check before relying on them.

- **Workers:**
  - 100,000 requests a day;
  - 10 ms of CPU per request;
  - 50 subrequests per request.
- **D1:**
  - 500 MB per database, 10 databases;
  - 2 MB per row or BLOB, 100 KB per SQL statement;
  - 50 queries per invocation;
  - 5M rows read and 100k rows written per day;
  - Time Travel point-in-time restore for 7 days.

  Limits return errors and never bill.
- **Durable Objects:**
  - available on the free plan, SQLite backend only;
  - 100,000 requests a day, 13,000 GB-s a day, 5 GB storage;
  - incoming WebSocket messages count at a 20:1 ratio;
  - hibernation is supported.
- **R2:** 10 GB free, but **enabling it requires a payment method**. Avoid it until the paid phase.
- **Workers Paid:**
  - $5/month;
  - 10M requests a month and 30M CPU-ms a month;
  - D1: 25B rows read a month and 50M written; 30-day Time Travel.

## Design rules forced by those limits

- **The server only checks and stores.** Anything CPU-heavy runs in the browser:
  - notebook conversion (in the uploader's browser);
  - Python (Pyodide);
  - rendering.
- **Static assets are public by design.** Never put protected content in static assets. Lab
  content comes from `/api` after a permission check.
- **Files live in D1** as chunks of 2 MB or less until R2 is enabled (paid phase).
- **One shared D1 database for all tenants,** with `org_id` on every tenant-owned table. A
  database per tenant is only an option later, for large customers.
- **Batch writes:** stay under 50 queries per request.
  - Bulk student import is chunked by the client.
  - Passwords are generated and hashed in the pedagog's browser. The plaintext only goes onto the
    printed slips and never reaches the server.

## Tenancy and permissions

- **Every query goes through a data-access layer that requires a tenant context:**
  `forTenant(db, orgId)` in `src/api/db/tenant.ts` adds the organization to every query. Biome
  blocks Drizzle and schema imports in `src/api` outside `src/api/db`, so handlers cannot run raw
  queries.
- **The database enforces it too:**
  - every tenant-owned table has `org_id`, and children reference parents by
    `(parent_id, org_id)` → `(id, org_id)`, so a row can never link to another organization;
  - every unique index on a tenant table includes `org_id`, so a uniqueness error never reveals
    another organization's data.
- **Another organization's resource looks missing:** reads return nothing, writes throw
  `NotFoundError`, and the API answers the same 404 as for a route that does not exist.
- **Cross-tenant isolation tests are mandatory:** every resource is listed in
  `test/api/tenant-isolation.test.ts` (get, list, update, delete, and links to another
  organization).
- **IDs** are random (UUIDv7), never sequential.
- **Permission model** (built in #9):
  - Capabilities are strings in `src/shared/capabilities.ts`: code checks them, so a new
    capability needs code.
  - Roles are rows in `roles` (key, name, capabilities as JSON), so a new role needs no code.
    The built-in templates are seeded by migration 0003. Changing one means a new migration.
  - A membership gives its role in one scope:
    - the organization: everywhere in it;
    - a course: that course and all its groups;
    - a group: that group only.
  - Organization routes live under `/api/orgs/:org` (the slug). The `tenantAccess` middleware
    resolves the organization, `c.var.tenant` (`forTenant`) and `c.var.access` from the user's
    memberships, read on every request. A non-member gets the same 404 as a missing
    organization.
  - Checks: `requireCapability(cap, target)`, or `c.var.access.can(cap, { courseId, groupId })`
    once the resource is loaded. Always pass the course of a group, so course roles apply. A
    missing capability answers 403.
  - `GET /api/orgs/:org/access` gives the app the user's capabilities by scope, for hiding
    actions.
  - Give teaching roles at course or group scope. An organization-wide role reaches every course:
    an organization-wide student would see all of them. So students get group memberships, by
    join code or by import (#11).
  - Built-in templates (the specification is `ROLES` in `test/api/roles.test.ts`):

    | Capability | admin | coordinator | pedagog | assistant | student |
    |---|---|---|---|---|---|
    | `org.manage`, `staff.approve` | ✓ | | | | |
    | `analytics.view`, `course.create` | ✓ | ✓ | ✓ | | |
    | `course.template.edit` | | ✓ | | | |
    | `course.manage`, `lab.publish`, `grade.edit`, `ai.configure` | | ✓ | ✓ | | |
    | `solution.view`, `student.manage`, `submission.review`, `live.host` | | ✓ | ✓ | ✓ | |
    | `lab.view` | | ✓ | ✓ | ✓ | ✓ |
    | `submission.create` | | | | | ✓ |
- **The UI may hide what a user can't do, but the API always enforces it.**

## Courses, groups and joining

Built in #10, under `/api/orgs/:org/courses` (`src/api/routes/courses.ts`).

- **Seeing a course:** staff of the course (`lab.view` or `course.manage` in it) or a student of
  one of its groups. Everyone else gets 404, as for a course that does not exist.
- **Creating** needs `course.create`, and the creator becomes the course's pedagog.
  `copyFromCourseId` copies last year's labs and template, but not its groups, members or
  visibility. The course, its pedagog and its labs are written in one batch.
- **Groups** (`course.manage`) each get a join code: 8 characters from an alphabet without
  look-alikes, shown as `XXXX-XXXX` (`src/shared/join-code.ts`).
  - Whoever may manage the group's students sees the code. They can replace it, which kills
    the old one at once, or switch joining off (`join_code` null).
  - Codes are unique across the platform: the code alone finds the group.
- **Joining** (`POST /api/join`): a signed-in user with a valid code becomes a student of that
  group, even in another organization, because the code is the invitation. Joining twice
  changes nothing. Codes of archived courses stop working. 10 wrong codes per user in
  15 minutes, then 429.
- **Archiving** (`course.manage`) ends the year: the course stays readable and is listed after
  the current ones. It can be undone.
- **Pages:**
  - `/courses`: my courses in every organization, "new course" for those with `course.create`;
  - `/o/:org/courses/:id`: the course; staff see each group's code, a full-screen QR view for
    the projector (lean-qr, always dark on white), new code / close registration, and delete;
  - `/join?code=…`: what the QR code opens. Signed-out students log in first and come back.

## Data model sketch

Built (#7; `src/api/db/schema.ts` is the source of truth):

```
organizations(id, name, slug)
users(id, username, full_name, email?, password_hash?, status)   -- global, one account for life
memberships(id, org_id, user_id, course_id?, group_id?, role)     -- scope: org, course or group
course_templates(id, org_id, title, owner_user_id?, version)     -- the coordinator's program
courses(id, org_id, template_id?, title, academic_year, archived_at?)
groups(id, org_id, course_id, name)
labs(id, org_id, course_id, n, title, week?, summary?, position)
lab_access(id, org_id, lab_id, group_id?, visible_from?, visible_until?, solutions_from?)
sessions(id = sha256(token), user_id, expires_at, last_seen_at, user_agent?)
```

Planned:

```
organizations + branding, settings
org_domains(org_id, domain, kind: staff|student, verified_at)
join codes on groups (#10)
notebooks(id, lab_id, kind: student|solution|extra, source_ipynb_ref, rendered_ref, sha256)
notebook_cells(notebook_id, idx, type, html, outputs_json, interactive, embed)  -- FTS5 index on text
files(id, org_id, name, mime, size, chunk_count) + file_chunks(file_id, n, data)
submissions, exercise_results, live_sessions, ai_logs, analytics_events (later phases)
login_attempts(key, window_start, count)
```

Every table except users and sessions carries `org_id` directly. Organizations see users only
through memberships, and never their password hashes.

## Auth and sessions

Own module built from standard parts, following the Lucia / "Copenhagen Book" approach.

Built in #8: `src/api/auth/`, data access in `src/api/db/auth.ts`, routes in
`src/api/routes/auth.ts`.

- **Session token:**
  - 32 random bytes; only its SHA-256 is stored.
  - Sent as a `__Host-session` cookie: HttpOnly, Secure, SameSite=Lax, Path=/.
  - 30-day sliding expiry, renewed once less than 15 days are left, so an active session does
    not write to D1 on every request.
  - A disabled account loses its sessions at the next request. A daily cron removes expired
    sessions.
- **Passwords:**
  - PBKDF2-SHA256 through WebCrypto, 16-byte salt per hash, NFC-normalized input.
  - Stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`. A hash with old parameters is
    replaced at the next successful sign-in.
  - 15,000 iterations. Measured in production on 2026-10-08:
    - a warm login takes 5-7 ms of CPU (failed: median 5 ms), and a cold one about 17 ms;
    - at 40,000 iterations it was 8-11 ms warm and 20 ms cold, against the 10 ms budget;
    - each 1,000 iterations cost about 0.1 ms, as on an Apple M4. Most of a login is the rest
      of the request (validation, about 5 queries, the session), so shave that first if more
      headroom is needed.
  - Cloudflare caps PBKDF2 at 100,000. Strength comes mostly from the passwords: generated ones
    are 12 or more characters from an unambiguous alphabet.
  - Check CPU time with `npx wrangler tail lab-platform --format json` (`cpuTime`) after
    changing anything on the sign-in path.
  - Unknown usernames are checked against a decoy hash, so they cost the same time as a wrong
    password, and the answer is the same.
- **CSRF:** SameSite=Lax plus an `Origin` check on every mutation (`sameOrigin` middleware).
- **Rate limiting:** failed sign-ins are counted in D1 (`login_attempts`), in fixed 15-minute
  windows:
  - 10 per username, which a correct password does not bypass;
  - 100 per IP, because a whole class shares the university's address.
  - The limits are checked before any hashing, and the answer is 429 with `Retry-After`.
- **First accounts:** `npm run account:create` (`scripts/create-account.ts`) creates an
  organization's first admin directly in D1. Everyone else is added in the app (#11).
- **Later:** email one-time codes (Resend); Google/Microsoft OAuth (Arctic); passkeys.

## Content pipeline

- **Upload:** a pedagog uploads a `.ipynb`.
  - Their browser converts it with the same rules as `site/scripts/notebook.mjs`, ported to
    isomorphic TypeScript in `src/notebook`. GUI cells (pygame, tkinter, subprocess, widgets)
    keep no outputs; errors, stderr and `⏳` lines are dropped.
  - Rendered cells and the original are stored.
- **Display:**
  - Cell HTML is sanitized with DOMPurify before it is shown.
  - Solution notebooks are served only with `solution.view`, or after `solutions_from`.
- **Embeds** (cell → visualization + props) are stored as data. The admin UI edits them.
- **Re-render all:** an admin action that re-converts the originals when the converter improves.

## Search

D1 FTS5 over cell text, joined with `lab_access` and the user's memberships. Results only include
what the user may see. Pagefind is not used in the platform.

## Quality, deploy, backups

- **Tests:**
  - Vitest in the Workers runtime: API, permissions, tenant isolation.
  - Playwright end-to-end, porting the ideas from `site/scripts/qa.mjs`: every lab renders,
    visualizations respond, mobile at 375px has no overflow, hydration is clean.
  - Biome for lint and format.
- **CI/CD:**
  - On every PR, GitHub Actions runs lint, typecheck, the migration and route-tree checks,
    tests, the build and the end-to-end tests.
  - On `main`, once all of that passes, it applies the D1 migrations (`--remote`), deploys
    (`npm run deploy`) and checks `/api/health` on the live site. Runs on `main` are never
    cancelled midway.
  - Migrations run before the new code goes live, so they must be additive: never rename or
    drop what the running code still uses in the same release.
  - The GitHub token (Workers Editor, D1 Write, Workers Observability Write, Account Settings
    Read) can deploy and migrate, but cannot create or delete Workers. A new Worker needs one
    deploy with the owner's `wrangler login`.
  - Live at https://lab-platform.florjanimema.workers.dev until the product has a domain.
  - Later: preview versions for branches.
- **Data location:** the production D1 database was created with the EU jurisdiction, so it is
  stored and processed only in the EU. This cannot be changed after creation.
- **Backups:**
  - D1 Time Travel: restore to any minute of the last 7 days (30 on the paid plan).
  - Weekly (`.github/workflows/backup.yml`): `wrangler d1 export`, encrypted with the owner's
    age key before upload, kept 90 days as a private workflow artifact. GitHub never sees the
    plaintext. Never commit an export: it contains student data.
- **Observability:** Workers logs; Sentry's free tier later.

## Portability

- Hono runs on Node, Bun and Deno.
- Drizzle supports Postgres.
- Keep Cloudflare-specific code (D1, Durable Objects, AI, assets) behind small adapters, so
  leaving Cloudflare is a port, not a rewrite.

## Privacy

- **Minimal personal data:** full name, username, optional email.
- **Institutions own their data:** per-org export and delete.
- **Data sent to AI:** only the question and the code or output context, never names.
- **Before selling:** check the Albanian data-protection law (aligned with GDPR) and offer
  institutions a data processing agreement.
