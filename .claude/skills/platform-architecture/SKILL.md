# Platform architecture

Product decisions live in `platform-vision`; this skill covers how to build it.

## Stack

| Layer | Choice |
|---|---|
| Frontend | React + TypeScript SPA (Vite), TanStack Router, TanStack Query, HeroUI v3 + Tailwind v4, lucide-react |
| Notebook display | markdown-it + KaTeX + Shiki (same as `site/scripts/notebook.mjs`), DOMPurify on display, Plotly lazy-loaded |
| Visualizations | The 13 React visualizers + kit from `site/src/viz/`, in `src/viz`, each loaded lazily |
| API | Hono on Cloudflare Workers; Zod validation; typed client (Hono RPC) |
| Database | Cloudflare D1 (SQLite) through Drizzle ORM; migrations in git |
| Real-time | Durable Objects (SQLite-backed, WebSocket Hibernation) |
| Python | Pyodide in a Web Worker (see `platform-live-coding`) |
| AI | Provider-agnostic layer (see `platform-ai`) |
| Email (phase 5) | Resend (free: 3,000 a month, 100 a day) |
| Tooling | Wrangler + `@cloudflare/vite-plugin`, Vitest (`@cloudflare/vitest-pool-workers`), Playwright, Biome, GitHub Actions |

- One Worker serves both the SPA's static assets and `/api/*`. Same origin means no CORS and
  simple cookies.
- Language: TypeScript everywhere.
- Repo layout (`goldenFlori/lab-platform`, private):
  - `src/web` (React SPA), with file-based routes in `src/web/routes`
  - `src/api` (Hono Worker), with `src/api/db` (Drizzle schema and access)
  - `migrations/` (D1, generated by drizzle-kit)
  - `test/` (Vitest inside workerd) and `e2e/` (Playwright)
  - `src/shared` (Zod schemas and types for the API and the app; the app imports only types)
  - `src/notebook`: the notebook converter (#13), which runs in the browser.
  - `src/viz`: the 13 visualizations and their kit (#14).
- Version pins with a reason:
  - **Vitest 4.x:** `@cloudflare/vitest-pool-workers` 0.22 does not support Vitest 5 yet.
  - **TypeScript 5.9:** TypeScript 7 (the native compiler) is out; upgrade deliberately, not in
    passing.
  - **Drizzle 0.45 / drizzle-kit 0.31:** 1.0 is still a release candidate (checked 2026-10-06). It
    moves each migration into its own folder, which needs `migrations_pattern` in
    `wrangler.jsonc`, so upgrade deliberately.
  - **`compatibility_date`:** never newer than the test runtime's workerd supports
    (2026-08-22 today), otherwise the tests fail to start.

## Free-tier limits

Verified 2026-10-06. Re-check before relying on them.

- **Workers:**
  - 100,000 requests a day;
  - 10 ms of CPU per request;
  - 50 subrequests per request.
- **D1:**
  - 500 MB per database, 10 databases;
  - 2 MB per row or BLOB, 100 KB per SQL statement;
  - 50 queries per invocation;
  - 5M rows read and 100k rows written per day;
  - Time Travel point-in-time restore for 7 days.

  Limits return errors and never bill.
- **Durable Objects:**
  - available on the free plan, SQLite backend only;
  - 100,000 requests a day, 13,000 GB-s a day, 5 GB storage;
  - incoming WebSocket messages count at a 20:1 ratio;
  - hibernation is supported.
- **R2:** 10 GB free, but **enabling it requires a payment method**. Avoid it until the paid phase.
- **Workers Paid:**
  - $5/month;
  - 10M requests a month and 30M CPU-ms a month;
  - D1: 25B rows read a month and 50M written; 30-day Time Travel.

## Design rules forced by those limits

- **The server only checks and stores.** Anything CPU-heavy runs in the browser:
  - notebook conversion (in the uploader's browser);
  - Python (Pyodide);
  - rendering.
- **Static assets are public by design.** Never put protected content in static assets. Lab
  content comes from `/api` after a permission check.
- **Files live in D1** as chunks of 2 MB or less until R2 is enabled (paid phase).
- **One shared D1 database for all tenants,** with `org_id` on every tenant-owned table. A
  database per tenant is only an option later, for large customers.
- **Batch writes:** stay under 50 queries per request.
  - Bulk student import is chunked by the client.
  - Passwords are generated and hashed in the pedagog's browser. The plaintext only goes onto the
    printed slips and never reaches the server.

## Tenancy and permissions

- **Every query goes through a data-access layer that requires a tenant context:**
  `forTenant(db, orgId)` in `src/api/db/tenant.ts` adds the organization to every query. Biome
  blocks Drizzle and schema imports in `src/api` outside `src/api/db`, so handlers cannot run raw
  queries.
- **The database enforces it too:**
  - every tenant-owned table has `org_id`, and children reference parents by
    `(parent_id, org_id)` → `(id, org_id)`, so a row can never link to another organization;
  - every unique index on a tenant table includes `org_id`, so a uniqueness error never reveals
    another organization's data.
- **Another organization's resource looks missing:** reads return nothing, writes throw
  `NotFoundError`, and the API answers the same 404 as for a route that does not exist.
- **Cross-tenant isolation tests are mandatory:** every resource is listed in
  `test/api/tenant-isolation.test.ts` (get, list, update, delete, and links to another
  organization).
- **IDs** are random (UUIDv7), never sequential.
- **Permission model** (built in #9):
  - Capabilities are strings in `src/shared/capabilities.ts`: code checks them, so a new
    capability needs code.
  - Roles are rows in `roles` (key, name, capabilities as JSON), so a new role needs no code.
    The built-in templates are seeded by migration 0003. Changing one means a new migration.
  - A membership gives its role in one scope:
    - the organization: everywhere in it;
    - a course: that course and all its groups;
    - a group: that group only.
  - Organization routes live under `/api/orgs/:org` (the slug). The `tenantAccess` middleware
    resolves the organization, `c.var.tenant` (`forTenant`) and `c.var.access` from the user's
    memberships, read on every request. A non-member gets the same 404 as a missing
    organization.
  - Checks: `requireCapability(cap, target)`, or `c.var.access.can(cap, { courseId, groupId })`
    once the resource is loaded. Always pass the course of a group, so course roles apply. A
    missing capability answers 403.
  - `GET /api/orgs/:org/access` gives the app the user's capabilities by scope, for hiding
    actions.
  - Give teaching roles at course or group scope. An organization-wide role reaches every course:
    an organization-wide student would see all of them. So students get group memberships, by
    join code or by import (#11).
  - Built-in templates (the specification is `ROLES` in `test/api/roles.test.ts`):

    | Capability | admin | coordinator | pedagog | assistant | student |
    |---|---|---|---|---|---|
    | `org.manage`, `staff.approve` | ✓ | | | | |
    | `analytics.view`, `course.create` | ✓ | ✓ | ✓ | | |
    | `course.template.edit` | | ✓ | | | |
    | `course.manage`, `lab.publish`, `grade.edit`, `ai.configure` | | ✓ | ✓ | | |
    | `solution.view`, `student.manage`, `submission.review`, `live.host` | | ✓ | ✓ | ✓ | |
    | `lab.view` | | ✓ | ✓ | ✓ | ✓ |
    | `submission.create` | | | | | ✓ |
- **The UI may hide what a user can't do, but the API always enforces it.**

## Courses, groups and joining

Built in #10, under `/api/orgs/:org/courses` (`src/api/routes/courses.ts`).

- **Seeing a course:** staff of the course (`lab.view` or `course.manage` in it) or a student of
  one of its groups. Everyone else gets 404, as for a course that does not exist.
- **Creating** needs `course.create`, and the creator becomes the course's pedagog.
  `copyFromCourseId` copies last year's labs and template, but not its groups, members or
  visibility. The course, its pedagog and its labs are written in one batch.
- **Groups** (`course.manage`) each get a join code: 8 characters from an alphabet without
  look-alikes, shown as `XXXX-XXXX` (`src/shared/join-code.ts`).
  - Whoever may manage the group's students sees the code. They can replace it, which kills
    the old one at once, or switch joining off (`join_code` null).
  - Codes are unique across the platform: the code alone finds the group.
- **Joining** (`POST /api/join`): a signed-in user with a valid code becomes a student of that
  group, even in another organization, because the code is the invitation. Joining twice
  changes nothing. Codes of archived courses stop working. 10 wrong codes per user in
  15 minutes, then 429.
- **Archiving** (`course.manage`) ends the year: the course stays readable and is listed after
  the current ones. It can be undone.
- **Pages:**
  - `/courses`: my courses in every organization, "new course" for those with `course.create`;
  - `/o/:org/courses/:id`: the course; staff see each group's code, a full-screen QR view for
    the projector (lean-qr, always dark on white), new code / close registration, and delete;
  - `/join?code=…`: what the QR code opens. Signed-out students log in first and come back.

## Labs and visibility

Built in #12, under `/api/orgs/:org/courses/:courseId/labs` (`src/api/routes/labs.ts`). The rules
are in `src/shared/lab-visibility.ts`.

- **A rule** (`lab_access`) belongs to a lab and one group, or the whole course (`group_id`
  null). A group's own rule wins over the course-wide one.
- **No rule, or `visible_from` null, means hidden.** Otherwise the lab is scheduled before
  `visible_from`, open until `visible_until`, and closed after it.
- **Solutions** are open to students only while the lab is open and from `solutions_from` on.
  Staff always see them.
- **Staff** are those with `solution.view` in the course: pedagog, coordinator, and assistants
  of its groups. They see every lab, with its state per group.
- **Students** see only labs open to one of their groups right now. Any other lab answers 404,
  also by direct link. Rules are read on every request, so a switch applies at once.
- **Changing:** labs (add, rename, renumber, remove) need `course.manage`. Rules need
  `lab.publish` in their scope: the course, or the group.
- **On the course page** (`CourseLabs`):
  - staff see each lab's state as chips (course, and any group with its own rule), a "Hapur"
    switch for the whole course, and an "Orari" panel with per-group rules, closing time and
    solutions date;
  - students see only the open labs.
  - Dates are written out in Albanian by `formatMoment`, not by Intl: not every browser
    carries Albanian locale data.

## Importing students

Built in #11. Pages: the group's students (`…/groups/:id`) and the import (`…/groups/:id/import`).

- **In the pedagog's browser:**
  - the class list is read from pasted text (Excel or Sheets columns, CSV, one name per line),
    a CSV or an `.xlsx` file (read-excel-file, loaded only for Excel);
  - each name gets a username base (`usernameBase`: first and last name, no accents) and a
    12-character password (lowercase and digits without look-alikes);
  - each password is hashed here with the same PBKDF2 code (`src/shared/password.ts`).
  - **Only hashes reach the server.** Plain passwords exist only on screen and on the printed
    slips (`CredentialSlips`: a print-only copy, A4, 10 per page, cut lines). There is no
    digital export, and the page warns before it is left unprinted.
- **On the server** (`POST …/groups/:id/students`, `student.manage`):
  - at most 25 students per request (`IMPORT_CHUNK`), and the browser sends a class in
    several requests;
  - the hash must have today's parameters (`isValidPasswordHash`);
  - usernames are numbered where taken anywhere on the platform (`arben.hoxha2`);
  - one select plus multi-row inserts of 10 rows (`ROWS_PER_INSERT`), all in one batch;
  - imported students get a group membership only.
- **Password reset** (`POST …/students/:id/password`): only for a student of that group. The
  new hash also comes from the browser, and the student's sessions end.

## Auth and sessions

Own module built from standard parts, following the Lucia / "Copenhagen Book" approach.

Built in #8: `src/api/auth/`, data access in `src/api/db/auth.ts`, routes in
`src/api/routes/auth.ts`.

- **Session token:**
  - 32 random bytes; only its SHA-256 is stored.
  - Sent as a `__Host-session` cookie: HttpOnly, Secure, SameSite=Lax, Path=/.
  - 30-day sliding expiry, renewed once less than 15 days are left, so an active session does
    not write to D1 on every request.
  - A disabled account loses its sessions at the next request. A daily cron removes expired
    sessions.
- **Passwords:**
  - PBKDF2-SHA256 through WebCrypto, 16-byte salt per hash, NFC-normalized input.
  - Stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`. A hash with old parameters is
    replaced at the next successful sign-in.
  - 15,000 iterations. Measured in production on 2026-10-08:
    - a warm login takes 5-7 ms of CPU (failed: median 5 ms), and a cold one about 17 ms;
    - at 40,000 iterations it was 8-11 ms warm and 20 ms cold, against the 10 ms budget;
    - each 1,000 iterations cost about 0.1 ms, as on an Apple M4. Most of a login is the rest
      of the request (validation, about 5 queries, the session), so shave that first if more
      headroom is needed.
  - Cloudflare caps PBKDF2 at 100,000. Strength comes mostly from the passwords: generated ones
    are 12 or more characters from an unambiguous alphabet.
  - Check CPU time with `npx wrangler tail lab-platform --format json` (`cpuTime`) after
    changing anything on the sign-in path.
  - Unknown usernames are checked against a decoy hash, so they cost the same time as a wrong
    password, and the answer is the same.
- **CSRF:** SameSite=Lax plus an `Origin` check on every mutation (`sameOrigin` middleware).
- **Rate limiting:** failed sign-ins are counted in D1 (`login_attempts`), in fixed 15-minute
  windows:
  - 10 per username, which a correct password does not bypass;
  - 100 per IP, because a whole class shares the university's address.
  - The limits are checked before any hashing, and the answer is 429 with `Retry-After`.
- **First accounts:** `npm run account:create` (`scripts/create-account.ts`) creates an
  organization's first admin directly in D1. Everyone else is added in the app (#11).
- **Later:** email one-time codes (Resend); Google/Microsoft OAuth (Arctic); passkeys.

## Content pipeline

- **Upload:** a pedagog uploads a `.ipynb` on the lab page (**Ngarko fletore**), as the lab's
  main notebook, supplementary material or a solution (`src/web/lib/upload-notebook.ts`).
  - Their browser converts it with `renderNotebook` (`src/notebook`, #13), a TypeScript port of
    the course site's `site/scripts/notebook.mjs`. GUI cells (pygame, tkinter, subprocess,
    widgets) keep no outputs; errors, stderr and `⏳` lines are dropped.
  - The same libraries at the same versions as the site: markdown-it 15.0.2, KaTeX 0.18.7,
    `@mdit/plugin-katex` 1.1.1, Shiki 4.4.3. Shiki uses Oniguruma (WebAssembly), because its
    JavaScript engine highlights differently after Albanian letters such as "ë".
  - So the converter runs in browsers, never in the Worker, which cannot compile WebAssembly
    at run time. Its tests run in Node (the `notebook` Vitest project).
  - Load it lazily. It is about 400 KB gzipped, mostly the Oniguruma engine (232 KB).
  - **The specification:** `test/notebook/fixtures` holds the 19 course notebooks and the
    site converter's output for each (HTML as fingerprints). Every one must match.
    `scripts/snapshot-course-notebooks.ts` rewrites the snapshots from the course repo. Do it
    only on purpose.
  - **Storage** (#14), `src/api/routes/notebooks.ts`:
    - a lab has notebooks (`main`, `extra` or `solution`);
    - each notebook has files: `notebook.ipynb` (the original), `rendered.json` (the converted
      cells) and its images and figures under the converter's names;
    - files are kept in `file_chunks` of at most 512 KB, since D1 allows 2 MB per value.
  - **Gzip end to end:** the browser gzips the converted cells (up to 1.5 MB raw for the course
    notebooks, about ten times smaller gzipped) and Plotly figures before upload. The Worker
    serves them as stored, with `Content-Encoding: gzip` and `encodeBody: "manual"`, so it
    never parses or re-encodes them. It unpacks only for clients that do not accept gzip.
  - **Upload in steps** within D1's limits: `POST` the notebook, `PUT` each file (at most
    10 MB), then `POST …/ready`. Until it is ready, only staff see it.
  - **Uploaded files never run code on our origin:** only an allowlist of types is accepted
    (JSON, ipynb, PNG, JPEG, GIF, SVG). Every file is served with `nosniff` and a sandboxing
    `Content-Security-Policy`, and the original downloads as an attachment.
- **Stored rendering:** `rendered.json` is a `StoredNotebook` (`src/notebook/stored.ts`): the
  converter's result without its assets, plus `format` (1 today). Bump the format when the shape
  changes, so that older renderings can be found and converted again.
- **Display** (#14): the lab page `/o/:org/courses/:courseId/labs/:labId`, with `?notebook=` for a
  lab's other notebooks. It looks like the course site's lab page: section cards, a table of
  contents, long code folded, outputs below their code.
  - **All notebook HTML goes through `sanitize()`** (`src/web/lib/sanitize.ts`, DOMPurify) before
    it is shown. `rendered.json` is made in a browser and could be hand-crafted, so the converter's
    own escaping is not enough. Scripts, event handlers, `javascript:` links, styles, forms and
    frames are removed, and links to other sites open in a new tab. An end-to-end test uploads a
    hostile rendering and checks that it stays harmless.
  - **Embeds:** an interactive cell (Pygame, Tkinter, widgets) shows its visualization first, with
    the code folded under it. Otherwise the visualization follows the last cell made from that
    notebook cell.
  - **Images** load from the notebook's files with the reader's session. **Plotly** (4.8 MB)
    ships as its own file and loads with the first figure that comes near the screen; figures
    follow the theme. KaTeX's styles and fonts load with the lab page.
  - Solution notebooks are served only with `solution.view`, or after `solutions_from`.
  - Not yet: folding saved outputs as a spoiler. The course site did this for one homework
    notebook, whose saved chart gives the answer away. Nor replacing a notebook with a new
    version while keeping its visualizations: today it is deleted and uploaded again.
- **Embeds** (cell → visualization + props) are stored as data: `embeds`, one per cell, from
  the 13 ids in `src/shared/visualizers.ts`, replaced as a whole with
  `PUT …/notebooks/:id/embeds`.
  - Staff edit them above the notebook. Each cell is listed by its heading, or for code by the
    section it belongs to, since a first line such as an import rarely says which exercise it is.
  - Props are typed as JSON for now; a form per visualization can come when pedagogs need it.
  - The course site's own embeds are in `test/notebook/fixtures/embeds.json`, copied by the
    snapshot script.
- **Re-render all:** an admin action that re-converts the originals when the converter improves.
- **Course import** (#16), `scripts/import-course.ts` (`npm run course:import`):
  - It reads a course site in the course repo's format: `site/content/course.mjs` (labs,
    resources, homework, embeds), the notebooks, and the solutions in `zgjidhjet/`.
  - `scripts/course-import/plan.ts` converts everything in Node; `apply.ts` uploads it through
    the API, signed in as a pedagog. So it runs the same permission checks and upload steps as the
    app, and works the same against `npm run dev` and production.
  - The plan:
    - resources become `main` or `extra` notebooks, titled without the "Laboratori N —" prefix;
    - homework becomes an `extra` notebook of its lab;
    - `X-ZGJIDHJE.ipynb` becomes the `solution` of `X.ipynb`, only if `isSolutionOf` holds, and
      takes its embeds.
  - **Sections:** a resource with `sections` (labs 5 and 6 share `laborator-05.ipynb` on the
    site) gives each lab its own `.ipynb` of whole cells (`laborator-05-laboratori-6.ipynb`).
    Each range starts at a heading that opens its cell. The embeds are renumbered for the part,
    and a rule above the part's first heading is dropped, as on the site.
  - **Re-running:**
    - a lab is matched by its number and its imported notebooks by file name;
    - if any of a lab's notebooks changed (file, title, kind or order), they are all uploaded
      again in order;
    - otherwise only differing embeds are written;
    - notebooks added in the app are left alone;
    - visibility is never touched.
  - The Node scripts run TypeScript as is, so `src/notebook/index.ts` imports its modules with
    `.ts` extensions.
  - `test/notebook/fixtures/course.json` is the site's labs and homework, written by the snapshot
    script.

## Visualizations

- **Ported from the course site** (`site/src/viz`) with the same behaviour. The only changes are
  lint and accessibility fixes.
- **Loading:** `src/viz/index.ts` maps each id in `src/shared/visualizers.ts` to a lazy component.
  Their names and one-line summaries are messages (`viz.names`, `viz.summaries`) in both languages.
  - Each visualization is its own chunk (2–9 KB gzipped), plus the shared kit.
  - `VizEmbed` loads one when it comes within 300 px of the screen.
  - An error boundary keeps a failing one from taking the page down. The usual cause is a deploy:
    an open tab's old chunks are gone, so it offers a reload.
- **Props** from an embed override the defaults (preset, mode, values). An unknown preset falls
  back to the first one.
- **Public gallery** at `/visualizations` and `/visualizations/:id`. The visualizations are
  platform content, not tenant data.
- **Accessibility:**
  - Each visualization is a region named by its title.
  - Keys from its controls bubble up to it for the shortcuts: ← and → step, Space plays, Home
    and End jump.
  - A graph canvas with clickable vertices or edges is a group of keyboard buttons; otherwise it
    is an image. Only a canvas with draggable vertices blocks touch scrolling.
  - With HeroUI, put a `Button` directly inside `<Tooltip>`. `Tooltip.Trigger` wraps it in a
    second focusable "button", which doubles every tab stop.
- **Tests:** the end-to-end tests open all 13 on desktop and at 375 px. Each must have no errors,
  must step forward, and must not overflow.

## Languages

Built in #19: the interface in Albanian and English, Albanian first.

- **Messages** (`src/web/i18n`):
  - `sq.ts` is the source, plain objects grouped by screen; a message with values is a function
    (`count: (n) => …`), which also handles plurals.
  - `en.ts` is typed as `Messages`, so a missing or extra English message fails the build. No
    i18n library and no extraction step.
  - `useT()` in components (re-renders on a switch); `t()` outside React, for page titles in
    `head` and error texts. Both dictionaries ship in the main bundle (a few KB gzipped).
  - Dates are spelled from the messages' month names rather than Intl, because not every browser
    carries Albanian locale data.
  - Course content is never translated: notebooks, course, lab and group names stay as written.
- **Which language** (`useLocaleSync` in `src/web/lib/locale.ts`):
  1. the user's own choice: `users.locale`, set with `PATCH /api/me` from the account menu;
  2. else this device's choice (`localStorage.locale`), which visitors set with the header's
     toggle;
  3. else the language of the course on screen: `courses.locale`, set on the course page by
     whoever manages it, or in the new-course form;
  4. else Albanian.

  A switch updates `<html lang>` and re-runs the routes so page titles follow.
- **Tests:**
  - an end-to-end test goes through every staff screen in English, as well as the visitor's
    toggle, the account preference and a course's language;
  - it fails on Albanian letters or common Albanian interface words in visible text or
    accessible labels (course content excluded);
  - each of the 13 visualizations is opened in English and stepped once, and must contain no
    common Albanian words (place names such as Tiranë are allowed);
  - API tests cover the settings.
- **Visualizations** (`src/viz/kit/text.ts`):
  - each visualization keeps its own `TEXT = bilingual(sq, en)` beside it, so its text loads with
    its chunk rather than with every page; `useText(TEXT)` picks the interface language;
  - `bilingual()` types English against Albanian, so a missing message fails the build;
  - the algorithm modules (`algorithms/*.ts`) take their step text as a parameter, from
    `algorithms/*.text.ts`, with Albanian as the default for callers that ignore the notes;
  - pseudocode is translated word for word, keeping the lecture's structure;
  - names stay as they are: Albanian cities, people and the lab notebooks' own vertex names
    (Hidranti, Qyteti…), which students compare with their notebooks;
  - descriptive vertex names (the flowers, the house and pasta steps) get English labels; the
    flowers name the vertices outright, so the steps read in the interface language too;
  - the embed's own title comes from the course and stays as the course wrote it.

## Search

Built in #17. A ⌘K palette (also Ctrl+K, `/`, or the header's button) searches labs, notebook
sections and the visualizations as you type.

- **No FTS5:** D1 cannot export a database that has virtual tables, and the weekly encrypted
  backup is an export. The course is small (19 notebooks: about 340 sections and 150 KB of
  text), so plain rows and matching in the browser are enough. Pagefind is not used.
- **Index** (`src/notebook/search.ts`): made where a notebook is converted (the pedagog's browser,
  or the course import).
  - One section per heading: its anchor, title, plain text (math as its TeX source, KaTeX's drawn
    copy left out) and the functions and classes its code defines. Outputs are not indexed.
  - Limits are in `src/shared/search-limits.ts`: at most 400 sections of 4,000 characters.
  - Stored in `search_sections` with `PUT …/notebooks/:id/search` (staff), replaced as a whole in
    one request (41 statements at most).
  - Notebooks uploaded before #17 have no index until uploaded again. The course import rewrites
    the index of every notebook it keeps.
- **Who sees what:** `GET /api/orgs/:org/courses/:id/search` returns the labs, ready notebooks and
  sections the user may see, by the lab pages' own rules (`labContext`, `openToViewer`,
  `mayReadNotebook`).
  - Students get only labs open to their groups now, and solutions only once open; staff get
    every lab.
  - A hidden lab's text never leaves the server, so the browser searches what it receives
    without further checks.
  - API tests prove it, with the schedule, solutions and other organizations.
- **Matching** (`src/web/lib/search-text.ts`):
  - case and Albanian accents are ignored (`fold` keeps every character in place, so matches are
    marked in the original text);
  - every term must start a word;
  - a section's title weighs more than its function names, which weigh more than its text;
  - a lab whose name matches comes first.
- **Loading:** the palette is its own chunk (5 KB gzipped), loaded on first open. It fetches one
  index per current course of each of the user's organizations, cached for 5 minutes, so typing
  costs the database nothing.
- **A section result** opens the lab at `?notebook=…#anchor`. The lab page scrolls to the hash
  once the notebook has rendered, so shared links to a section work too.

## Analytics

Built in #18: weekly activity per course for staff with `analytics.view` (pedagogs, coordinators),
at `/o/:org/courses/:id/activity`, linked from the course page.

- **What counts** (`lab_activity`): a student opened a lab's notebook, downloaded its `.ipynb`,
  used one of its visualizations, or completed one of its exercises (#51; recorded when the
  completion is).
  - At most one row per student, lab, kind and day (`INSERT … ON CONFLICT DO NOTHING`), so a
    class of 120 stays at tens of thousands of rows a year.
  - Opening and downloading are recorded by the API as it serves the notebook's detail and its
    original file. A visualization is reported by the lab page (`POST …/labs/:id/activity`) on the
    first click or key inside one, once per notebook opened.
  - The writes go through `waitUntil`, after the response, so reading a lab never waits for them
    and never fails because of them.
  - Staff are never recorded.
  - Days are in `Europe/Tirane` for now (`ACTIVITY_TIME_ZONE`), and weeks run Monday to Sunday.
    A time zone per institution comes with self-service institutions.
- **The report** (`GET …/courses/:id/activity[?group=]`):
  - students of the groups the user may see: the whole course with a course-wide grant, or only
    their own groups;
  - per week, from the week the course began (at most 26 weeks): students active at all, and per
    kind;
  - per lab, since the start;
  - all as counts made in SQL (`COUNT(DISTINCT user_id)`): no student is named, and the Worker
    does not loop over rows.
- **Not yet:**
  - analytics for the institution admin (who does not see courses);
  - code runs;
  - deleting old activity (see open items in `platform-vision`).

## Quality, deploy, backups

- **Tests:**
  - Vitest in the Workers runtime: API, permissions, tenant isolation.
  - Playwright end-to-end, porting the ideas from `site/scripts/qa.mjs`. The course is imported
    from the fixtures with the import's own code, which must give the site's labs, change nothing
    when run again, and keep hidden labs and solutions from students. Every one of the 19 course
    notebooks must then show each visualization,
    without errors or overflow at 375px, even with every letter 0.25px wider (text renders a
    little wider on CI's Linux than on a Mac); each visualization opens and steps; a pedagog's
    upload, embed editing and deletion run through the real UI.
  - Biome for lint and format.
- **CI/CD:**
  - On every PR, GitHub Actions runs lint, typecheck, the migration and route-tree checks,
    tests, the build and the end-to-end tests.
  - On `main`, once all of that passes, it applies the D1 migrations (`--remote`), deploys
    (`npm run deploy`) and checks `/api/health` on the live site. Runs on `main` are never
    cancelled midway.
  - Migrations run before the new code goes live, so they must be additive: never rename or
    drop what the running code still uses in the same release.
  - The GitHub token (Workers Editor, D1 Write, Workers Observability Write, Account Settings
    Read) can deploy and migrate, but cannot create or delete Workers. A new Worker needs one
    deploy with the owner's `wrangler login`.
  - Live at https://lab-platform.florjanimema.workers.dev until the product has a domain.
  - Later: preview versions for branches.
- **Data location:** the production D1 database was created with the EU jurisdiction, so it is
  stored and processed only in the EU. This cannot be changed after creation.
- **Backups:**
  - D1 Time Travel: restore to any minute of the last 7 days (30 on the paid plan).
  - Weekly (`.github/workflows/backup.yml`): `wrangler d1 export`, encrypted with the owner's
    age key before upload, kept 90 days as a private workflow artifact. GitHub never sees the
    plaintext. Never commit an export: it contains student data.
- **Observability:** Workers logs; Sentry's free tier later.

## Portability

- Hono runs on Node, Bun and Deno.
- Drizzle supports Postgres.
- Keep Cloudflare-specific code (D1, Durable Objects, AI, assets) behind small adapters, so
  leaving Cloudflare is a port, not a rewrite.

## Privacy

- **Minimal personal data:** full name, username, optional email.
- **Learning activity** is kept per student and day only to count distinct students. Reports show
  counts, never names, and no third-party tracker is used.
- **Institutions own their data:** per-org export and delete.
- **Data sent to AI:** only the question and the code or output context, never names.
- **Before selling:** check the Albanian data-protection law (aligned with GDPR) and offer
  institutions a data processing agreement.
