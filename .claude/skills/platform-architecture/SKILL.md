# Platform architecture

Product decisions live in `platform-vision`; this skill covers how to build it.

## Stack

| Layer | Choice |
|---|---|
| Frontend | React + TypeScript SPA (Vite), TanStack Router, TanStack Query, HeroUI v3 + Tailwind v4, lucide-react |
| Notebook display | markdown-it + KaTeX + Shiki (same as `site/scripts/notebook.mjs`), DOMPurify on display, Plotly lazy-loaded |
| Visualizations | The 13 React visualizers + kit from `site/src/viz/`, in `src/viz`, each loaded lazily |
| API | Hono on Cloudflare Workers; Zod validation; typed client (Hono RPC) |
| Database | Cloudflare D1 (SQLite) through Drizzle ORM; migrations in git |
| Real-time | Durable Objects (SQLite-backed, WebSocket Hibernation) |
| Python | Pyodide in a Web Worker (see `platform-live-coding`) |
| AI | Provider-agnostic layer (see `platform-ai`) |
| Email (phase 5) | Resend (free: 3,000 a month, 100 a day) |
| Tooling | Wrangler + `@cloudflare/vite-plugin`, Vitest (`@cloudflare/vitest-pool-workers`), Playwright, Biome, GitHub Actions |

- One Worker serves both the SPA's static assets and `/api/*`. Same origin means no CORS and
  simple cookies.
- Language: TypeScript everywhere.
- Repo layout (`goldenFlori/lab-platform`, private):
  - `src/web` (React SPA), with file-based routes in `src/web/routes`
  - `src/api` (Hono Worker), with `src/api/db` (Drizzle schema and access)
  - `migrations/` (D1, generated by drizzle-kit)
  - `test/` (Vitest inside workerd) and `e2e/` (Playwright)
  - `src/shared` (Zod schemas and types for the API and the app; the app imports only types)
  - `src/notebook`: the notebook converter (#13), which runs in the browser.
  - `src/viz`: the 13 visualizations and their kit (#14).
- Version pins with a reason:
  - **Vitest 4.x:** `@cloudflare/vitest-pool-workers` 0.22 does not support Vitest 5 yet.
  - **TypeScript 5.9:** TypeScript 7 (the native compiler) is out; upgrade deliberately, not in
    passing.
  - **Drizzle 0.45 / drizzle-kit 0.31:** 1.0 is still a release candidate (checked 2026-10-06). It
    moves each migration into its own folder, which needs `migrations_pattern` in
    `wrangler.jsonc`, so upgrade deliberately.
  - **`compatibility_date`:** never newer than the test runtime's workerd supports
    (2026-08-22 today), otherwise the tests fail to start.

## Free-tier limits

Verified 2026-10-06. Re-check before relying on them.

- **Workers:**
  - 100,000 requests a day;
  - 10 ms of CPU per request;
  - 50 subrequests per request.
- **D1:**
  - 500 MB per database, 10 databases;
  - 2 MB per row or BLOB, 100 KB per SQL statement;
  - 50 queries per invocation;
  - 5M rows read and 100k rows written per day, reset at 00:00 UTC (re-checked 2026-10-27);
  - since 2026-09-01 queries fail once a day's limit is used, until the reset;
  - a write to an indexed column counts once for the table and once per index, so an upsert on a
    table with a unique index costs at least 2 rows;
  - Time Travel point-in-time restore for 7 days.

  Limits return errors and never bill. Past 100k requests a day, Workers answer with error 1027.
- **Durable Objects** (re-checked 2026-10-11):
  - available on the free plan, SQLite backend only;
  - 100,000 requests a day, 13,000 GB-s a day, 5 GB storage;
  - incoming WebSocket messages count at a 20:1 ratio;
  - hibernation is supported.
- **R2:** 10 GB free, but **enabling it requires a payment method**. Avoid it until the paid phase.
- **Workers Paid:**
  - $5/month;
  - 10M requests a month and 30M CPU-ms a month;
  - D1: 25B rows read a month and 50M written; 30-day Time Travel.

## Measured budget (#176)

`npm run measure:class` (`scripts/measure-class.ts`) builds the app, runs it on its own local database
with the meter on (`MEASURE=1`, never set in production; `src/api/db/meter.ts` counts every query's
rows from D1's meta), imports the course fixtures, adds 120 students, and measures each student action:
API calls as the app makes them, and page loads, reloads and returns to the tab in Chromium. It
multiplies them by a model of a lab hour and a 90-minute kolokium (its counts are in the script, with
their reasons) and prints the class's share of the daily limits. `MEASURE=queries` also logs each
query's rows, to find the costly ones. `test/api/meter.test.ts` keeps a save at one row written.

120 students, 2026-10-27, after #182 and #177 (worst case: every student types the whole time):

| | requests | rows read | rows written | classes a day |
|---|---|---|---|---|
| lab hour (60 min) | 15,960 (16%) | 0.35M (7%) | 19,320 (19%) | 5 |
| kolokium (90 min) | 18,240 (18%) | 0.80M (16%) | 33,120 (33%) | 3 |

Before #182 and #177: requests 50% and 62%, rows read 142% and 183%, rows written 39% and 59%.

- **Reads were 142% and 183% before #182.** Every request read about 140 rows before its work: 123
  were the user's memberships, scanned by organization because the indexes that start with the user
  are partial. `memberships_user_idx` (user_id, org_id) makes it a lookup of about 5 rows, whatever
  the class's size, and a test keeps it so. A request's own overhead is now about 20 rows.
- Staff following a kolokium read about 620 rows a poll (4 per student listed), about 4.5% of a day's
  reads per kolokium; the list polls only while its page is visible.
- **Partial indexes serve only queries whose WHERE implies theirs.** A lookup by user needs its own
  index even where unique partial ones start with the user.
- Opening a lab page is 12 requests and about 220 rows read. Returning to the tab reloads nothing
  (`refetchOnWindowFocus: false`, #177); it reloaded 8 queries before.
- **Saving work (#177):** code and graded trace rows wait in one queue per notebook
  (`src/web/lib/code-edits.tsx`) and go in one request, `PUT …/notebooks/:id/work`: 3 s after a
  change, at most once every 30 s, and at once when the page is hidden or left, the notebook changes
  or the student hands in. A hand-in waits for every save; a failed one stays queued and is tried
  again. The server writes it as multi-row upserts (at most 20 cells a request) and keeps trace rows
  only while the notebook is open to the student, naming the tables it refused. A cell's row costs 3
  rows written the first time (the row and two indexes), then 1. Before, each pause in typing (0.8 s,
  0.7 s for a table) was a request, and a hand-in did not wait for a table's save.
- **When a limit is reached anyway (#178):** D1's "exceeded D1's free tier daily row …" errors answer
  503 `daily_limit` with `Retry-After` until midnight UTC (`src/api/errors.ts`); past the requests
  limit Cloudflare answers its own 1027 page (non-JSON). Every API answer reports to
  `src/web/lib/service.ts`, and one banner says "no connection" or "today's limit, saved after HH:MM".
  The save queue keeps what waits in `localStorage` (`lab-work:<user>:<notebook>`,
  `src/web/lib/drafts.ts`) until it is saved, restores it on the next visit, retries every 10 minutes
  at the limit (30 s otherwise, at once when back online), and every copy goes at sign-out. A pressed
  hand-in waits and retries by itself; its time is the server's, never the browser's (which anyone
  could change), so one arriving after the deadline is refused and the pedagog may move it.

## What a lab room downloads (#190)

`npm run measure:room` (`scripts/measure-room.ts`, sharing `scripts/lib/local-platform.ts` with the
class measurement) opens a lab as a student in Chromium with the service worker on, and sorts every
byte over the network by part. Our own files are counted as Cloudflare sends them (brotli; the
estimate gives the engine 3.2 MB where production sends 3.5 MB). First run, 2026-10-29, one device:

| | download |
|---|---|
| sign in and open the lab (app, fonts, lab data) | 0.7 MB |
| the Python engine, at the first run (`pyodide.asm.wasm`, `python_stdlib.zip`, …) | 6.0 MB |
| the course's libraries (numpy, networkx, matplotlib, plotly, with their dependencies) | 25 MB |
| any later visit, also running code with the libraries | ~0 (service worker and HTTP cache) |

- The largest are plotly (9.7 MB, from PyPI), matplotlib (6.9 MB), the engine's wasm (3.2 MB),
  numpy (2.9 MB) and the standard library (2.5 MB). Packages come from jsDelivr (Pyodide's) and
  PyPI (plotly, through micropip), over the room's connection all the same.
- **A first class of 120 starting together pulls about 3.8 GB:** about 6 minutes on a full 100
  Mbit/s, half an hour on a crowded 20. Later classes download almost nothing. So the first download
  belongs before the first class (#191).
- A lab downloads only what its cells import; the 25 MB is the whole course's set.
- **The get-ready page (#191):** `/ready`, public, downloads it all once through the same Python as
  the lab page (so the service worker keeps it): a browser check (WebAssembly, workers,
  cross-origin isolation, free space; `navigator.storage.persist()` asked), the engine, then each of
  `COURSE_LIBRARIES` (`src/web/lib/device-ready.ts`), then a test run. Nothing starts until pressed.
  It marks the device ready per Pyodide version in `localStorage` (`__PYODIDE_VERSION__` is defined
  by Vite, so the app does not import Pyodide); the course page then stops prompting the student.
  Staff get the link and a QR code on the course page.

- **The server only checks and stores.** Anything CPU-heavy runs in the browser:
  - notebook conversion (in the uploader's browser);
  - Python (Pyodide);
  - rendering.
- **Static assets are public by design.** Never put protected content in static assets. Lab
  content comes from `/api` after a permission check.
- **The installable app (#89)** is a PWA: `public/manifest.webmanifest`, icons drawn by
  `scripts/make-app-icons.ts`, and a service worker (`src/web/pwa/sw.js`, built into `/sw.js`
  with the build and Pyodide versions).
  - The service worker never touches `/api`: protected content is never cached on a device.
  - Pages come from the network, and the offline page when there is none.
  - It keeps `/assets/*` per build, and the Python engine and packages per Pyodide version, with
    the PyPI wheels micropip installs (plotly; named by their hash, so never stale, #191).
  - Cached responses keep their COOP and COEP headers, so the app stays cross-origin isolated.
  - Cache only final responses. Cloudflare redirects `/offline.html` to `/offline`, and a
    redirected response may not answer a page.
  - The other end-to-end specs block service workers (`playwright.config.ts`).
  - A store app (Capacitor) waits until a real need appears.
- **Files live in D1** as chunks of 2 MB or less until R2 is enabled (paid phase).
- **One shared D1 database for all tenants,** with `org_id` on every tenant-owned table. A
  database per tenant is only an option later, for large customers.
- **Batch writes:** stay under 50 queries per request.
  - Bulk student import is chunked by the client.
  - Passwords are generated and hashed in the pedagog's browser. The plaintext only goes onto the
    printed slips and never reaches the server.

## Tenancy and permissions

- **Every query goes through a data-access layer that requires a tenant context:**
  `forTenant(db, orgId)` in `src/api/db/tenant.ts` adds the organization to every query. Biome
  blocks Drizzle and schema imports in `src/api` outside `src/api/db`, so handlers cannot run raw
  queries.
- **The database enforces it too:**
  - every tenant-owned table has `org_id`, and children reference parents by
    `(parent_id, org_id)` → `(id, org_id)`, so a row can never link to another organization;
  - every unique index on a tenant table includes `org_id`, so a uniqueness error never reveals
    another organization's data.
- **Another organization's resource looks missing:** reads return nothing, writes throw
  `NotFoundError`, and the API answers the same 404 as for a route that does not exist.
- **Cross-tenant isolation tests are mandatory:** every resource is listed in
  `test/api/tenant-isolation.test.ts` (get, list, update, delete, and links to another
  organization).
- **IDs** are random (UUIDv7), never sequential.
- **Permission model** (built in #9):
  - Capabilities are strings in `src/shared/capabilities.ts`: code checks them, so a new
    capability needs code.
  - Roles are rows in `roles` (key, name, capabilities as JSON), so a new role needs no code.
    The built-in templates are seeded by migration 0003. Changing one means a new migration.
  - A membership gives its role in one scope:
    - the organization: everywhere in it;
    - a course: that course and all its groups;
    - a group: that group only.
  - Organization routes live under `/api/orgs/:org` (the slug). The `tenantAccess` middleware
    resolves the organization, `c.var.tenant` (`forTenant`) and `c.var.access` from the user's
    memberships, read on every request. A non-member gets the same 404 as a missing
    organization.
  - Checks: `requireCapability(cap, target)`, or `c.var.access.can(cap, { courseId, groupId })`
    once the resource is loaded. Always pass the course of a group, so course roles apply. A
    missing capability answers 403.
  - `GET /api/orgs/:org/access` gives the app the user's capabilities by scope, for hiding
    actions.
  - Give teaching roles at course or group scope. An organization-wide role reaches every course:
    an organization-wide student would see all of them. So students get group memberships, by
    join code or by import (#11).
  - Built-in templates (the specification is `ROLES` in `test/api/roles.test.ts`):

    | Capability | admin | coordinator | pedagog | assistant | student |
    |---|---|---|---|---|---|
    | `org.manage`, `staff.approve` | ✓ | | | | |
    | `analytics.view`, `course.create` | ✓ | ✓ | ✓ | | |
    | `course.template.edit` | | ✓ | | | |
    | `course.manage`, `lab.publish`, `grade.edit`, `ai.configure` | | ✓ | ✓ | | |
    | `solution.view`, `student.manage`, `submission.review`, `live.host` | | ✓ | ✓ | ✓ | |
    | `lab.view` | | ✓ | ✓ | ✓ | ✓ |
    | `submission.create` | | | | | ✓ |
- **The UI may hide what a user can't do, but the API always enforces it.**

## The platform owner (#200)

- Owners are named by username in the Worker secret `PLATFORM_OWNERS` (comma-separated), never in the
  database, so no tenant can become one (`src/api/auth/owner.ts`). Tests set `owner.test`, the e2e
  server `e2e.staff`. `/api/me` says `owner: true` only to an owner.
- `/api/platform/*` (`src/api/routes/platform.ts`) answers 404 `not_found` to anyone else, as a route
  that does not exist. `GET /institutions`: every organization with counts made in SQL (courses;
  distinct staff and students by membership role; students with activity in the last 7 days).
  `POST /institutions`: the organization, its first admin (password hashed in the owner's browser)
  and the admin's organization-wide membership in one batch; `slug_taken` or `username_taken` (409).
- `/platform` (account menu → Platform) shows them and prints the admin's slip, as for students.
  `npm run account:create` stays for a new environment or an emergency.

## Institution branding (#201)

- `organizations` holds `accent` (#rrggbb), `logo` (bytes, at most 100 KB: PNG, JPEG, WebP or SVG),
  `logo_type` and `logo_version` (a timestamp that names the logo's URL, so it is cached for good).
- `src/shared/branding.ts` (no Zod) has the rule both sides use: an accent must give white text on it,
  itself as text on white, and itself on its 10% tint at least 4.5:1 (`accentIssue`).
- Members read `GET /api/orgs/:org/branding` and `/logo`; admins (`org.manage`) `PUT /branding`,
  `PUT`/`DELETE /logo` (raw body, type checked, 413 past the size). The logo is served `nosniff` with
  a sandboxing CSP, so an SVG cannot run code. The sign-in page reached from a join link reads
  `GET /api/join/:code/branding` and `/logo`: the code is the invitation; a code that joins nothing
  is a 404, so no institution is revealed without one.
- The app: on an institution's pages the header shows its logo and name and `data-org-accent` puts
  its accent in place of the platform's, in the light theme only (the dark theme's accent is made
  for it); the slips print its name; `/o/:org/admin` is its admin's page (#202 extends it); the
  institution's export carries the accent and the logo.

## The institution admin's page (#202)

`/o/:org/admin`, for those with `org.manage` (`src/api/routes/org-admin.ts`, under
`/api/orgs/:org/admin`, 403 to other members):
- **People:** a page of 50 by username with search (`tenant.people.page`), each with their role across
  the institution and counts of where they teach and study (SQL subqueries). `POST /people` makes a
  staff account with an institution role (admin, coordinator, pedagog; password hashed in the
  admin's browser, slip printed); `PUT /people/:id/role` gives, changes or takes away that role,
  never one's own (`own_account`): only an admin acts, so an institution keeps at least that admin.
  Someone whose only membership was that role leaves the institution; the account stays.
- **Settings:** `organizations.locale` (the language for people who chose none, outside courses with
  their own: user → device → course → institution → Albanian) and `ai_allowed`; off turns AI off in
  every course in the same batch, and a course's switch then answers `ai_not_allowed`. Both come to
  members with the branding.
- **Data:** the deletion requests and the export moved here from the courses page.
- Institution admins do not see inside courses (no `lab.view`): courses are their pedagogs'.

## Sharing a course (#203)

- **The link:** staff with `course.manage` share a course from its page (`PUT /api/orgs/:org/courses/:id/share`).
  `course_shares` holds one row per course: a 128-bit hex token, unique across the platform like a
  join code, and `solutions`, which only someone with `solution.view` may turn on. Stopping deletes
  the row, so the link dies; copies stay. Tokens are invitations: never exported.
- **Who may open it:** `GET /api/shares/:token` answers only users with an institution-wide role that
  has `course.create`; anyone else, like a wrong token, gets 404, so a link that reaches a student
  shows nothing. `POST /api/orgs/:org/courses/from-share` needs `course.create` there.
- **The copy** (`src/api/db/sharing.ts`, cross-tenant by design like `join.ts`): one D1 batch of about
  ten `INSERT … SELECT` statements, so the files' bytes never pass through the Worker and the count
  stays fixed. Old lab and notebook ids map to new ones through one JSON parameter each
  (`json_each`); rows under a notebook get UUIDv7 ids made in SQL; chunks find their new file by
  notebook and name. Each statement starts from its map (`CROSS JOIN` fixes the order), so it reads
  only the course's rows by index. Sent with `db.$client.batch`: Drizzle 0.45 cannot bind raw SQL
  in a batch.
- **What goes:** labs, ready notebooks with their files, embeds, exercises and search index; with
  `solutions`, also solution notebooks and `exercise_grading` (points and hidden tests). Never groups,
  visibility, memberships, work, grades or AI settings: labs arrive hidden and AI off.
- **Where it came from:** `courses.copied_from_course_id`, plus the title and institution as they
  were, which survive the original's deletion. The author sees the copies' institution, year and
  date (`copiesOf`), nothing else. The full course is about 8 MB of files, so each copy costs that
  much of the database's 500 MB free size.

## A new version of a notebook (#208)

Staff put a corrected .ipynb in place of a notebook from the lab's "More" menu; the notebook keeps its
id, so students' work stays. Deleting and uploading again would delete it all (cascade).
- **Matching** (`src/notebook/versions.ts`, in the browser): cells by place in the .ipynb (srcIndex).
  Identical cells first, in order (a longest common subsequence); between two of them, the rest are
  paired by type the same way and count as changed; the remainder is added or removed. Staff see the
  counts, each removed cell that holds work (students, from `GET …/cells/work`), a visualization or an
  exercise, and confirm.
- **Putting it in place:** the files go up as `next.<name>` (never served), then `POST …/version`
  runs one batch: the staged files replace the old ones, and every table kept by cell (embeds, code
  edits, exercises, completions, trace answers, first tries, grading, AI questions) moves to its new
  number. Rows move through negative numbers first, so no unique key meets itself; rows in a removed
  cell go, except AI questions. Hand-ins' code, solved cells and trace rows, and grades' results, are
  renumbered inside their JSON; scores stay. A variant trace table gets `seedCell` (its old cell), so
  every student keeps their graph (`seedCellOf`).
- **Versions in addresses:** a notebook's version is the first 12 hex characters of its .ipynb's
  SHA-256. `rendered.json` and the original are fetched with `?v=<version>`, since browsers keep files
  an hour; the lab page starts the rendering once the notebook list names it.
- **Students mid-edit:** every save names the page's version. The notebook keeps the previous version
  and its cell map, so a save from a page still showing it is renumbered; one from older is refused
  (`stale_version`, 409). The answer names the version now, and the page loads it. A device copy
  (#178) records its version and is sent under it, apart from the page. A student whose edited cell
  changed sees a note (`versionAt`, `changedCells`).
- **Left as they are:** live actions in flight on a page showing the old version (a check passed, a
  first try) are recorded under the old cell number.

## A notebook with one's own code (#214)

`src/notebook/with-code.ts` puts code into an .ipynb by cell (srcIndex), clearing those cells'
outputs and execution counts, which belong to the original code; nothing else changes. The browser
does it, from the original fetched with its version and the code it already has: a student's own
edits ("Shkarko versionin tim" in the edits bar, unsaved ones included) and, for staff who review, a
hand-in's code ("Shkarko si .ipynb"). No server work, and no new data leaves the platform.

## Hints written by the pedagog (#215)

- `exercises.hints` (JSON, up to 3 of 600 characters), edited with the exercise. Staff get the text
  with the notebook; students only `hintCount`, so a hint never reaches a student unrevealed.
- `POST …/exercises/:cell/hints/:n` reveals one, in order (409 out of order), and refuses students
  while a kolokium runs for their group (403), like AI help. A student's reveal is kept once in
  `hint_reveals` (per student, exercise, hint and day); staff are not recorded. `GET …/hints` gives
  the user's revealed hints with their current text.
- Staff with analytics get per-hint counts with the exercise progress, only when five or more
  students are counted. Reveals follow first tries everywhere: renumbered with a new version,
  erased with the person, in "My data" and the institution's export, deleted after two years; the
  privacy page and the agreement list them. A copied course keeps its hints.

## The demo institution (#216)

- It exists when an institution with the slug `demo` does (`src/shared/demo.ts`); only the owner makes
  one. Its oldest course is the template, imported by the owner.
- `resetDemo` (`src/api/db/demo.ts`), every night with the cron and on the owner's
  `POST /api/platform/demo/reset`: deletes the other courses (visitors' work goes with them), the demo
  accounts' memberships and sessions; copies the template (`copyCourse`, solutions included) with
  `demo.pedagog` as pedagog; adds "Grupi A" with `demo.studenti` and eleven made-up classmates (algorithm
  words as surnames), every lab open, and their activity, solved exercises, a hand-in and a released
  grade. Accounts are made once without passwords; a username someone in another institution has is
  left out. Rows go as one `INSERT … SELECT` from JSON per table (about 30 statements in all).
- `POST /api/demo/:role` signs a visitor in to the shared account (no password) and names the course;
  `GET /api/demo` says whether there is one. The front page offers it to visitors not signed in.
- `demoGuard` (after `session`): the two shared accounts may change only an allowlist (saving work,
  exercises, hints, visualizations, handing in, kolokium, opening labs, Live Labs, grading, the
  language, signing out); anything else answers 403 `demo_read_only`. So no accounts, uploads,
  deletions, shares or deletion requests come from a visitor. A banner tells them it is a shared demo
  rebuilt nightly, and not to type anything personal; the privacy page says so too.

## Courses, groups and joining

- **Staff** (#64, `src/api/routes/staff.ts`): staff with `course.manage` for the whole course list
  its pedagogs and assistants and add them for the course or one group: an account of the
  organization by username (another organization's accounts are never found), or a new account
  whose password is generated and hashed in the browser and shown once. One role per person in
  the course and in each group; the last course-wide pedagog cannot be removed.

Built in #10, under `/api/orgs/:org/courses` (`src/api/routes/courses.ts`).

- **Seeing a course:** staff of the course (`lab.view` or `course.manage` in it) or a student of
  one of its groups. Everyone else gets 404, as for a course that does not exist.
- **Creating** needs `course.create`, and the creator becomes the course's pedagog.
  `copyFromCourseId` starts a new term from a course the creator can see (#210), through the same
  `copyCourse` as sharing (#203): labs, ready notebooks with their files, embeds, exercises and
  search, and solutions with grading if the creator has `solution.view` there; its template too.
  Never groups, members, visibility or work. It records where it came from (`copiedFrom…`), and
  everything is written in one batch.
- **Groups** (`course.manage`) each get a join code: 8 characters from an alphabet without
  look-alikes, shown as `XXXX-XXXX` (`src/shared/join-code.ts`).
  - Whoever may manage the group's students sees the code. They can replace it, which kills
    the old one at once, or switch joining off (`join_code` null).
  - Codes are unique across the platform: the code alone finds the group.
- **Joining** (`POST /api/join`): a signed-in user with a valid code becomes a student of that
  group, even in another organization, because the code is the invitation. Joining twice
  changes nothing. Codes of archived courses stop working. 10 wrong codes per user in
  15 minutes, then 429.
- **Deleting** (`course.manage`, #80): "Fshi kursin" on the course page, after a popup that says
  what goes with it; `DELETE /courses/:id` removes the course and the database cascades to its
  groups, memberships, labs, notebooks and files, students' code, submissions, grades and activity.
  Accounts stay. Archiving remains the way to end a year without losing anything.
- **Archiving** (`course.manage`) ends the year: the course stays readable and is listed after
  the current ones. It can be undone.
- **Pages:**
  - `/courses`: my courses in every organization, "new course" for those with `course.create`;
  - `/o/:org/courses/:id`: the course; staff see each group's code, a full-screen QR view for

## Labs and visibility

Built in #12, under `/api/orgs/:org/courses/:courseId/labs` (`src/api/routes/labs.ts`). The rules
are in `src/shared/lab-visibility.ts`.

- **A rule** (`lab_access`) belongs to a lab and one group, or the whole course (`group_id`
  null). A group's own rule wins over the course-wide one.
- **No rule, or `visible_from` null, means hidden.** Otherwise the lab is scheduled before
  `visible_from`, open until `visible_until`, and closed after it.
- **Solutions** are open to students only while the lab is open and from `solutions_from` on.
  Staff always see them.
- **Staff** are those with `solution.view` in the course: pedagog, coordinator, and assistants
  of its groups. They see every lab, with its state per group.
- **Students** see only labs open to one of their groups right now. Any other lab answers 404,
  also by direct link. Rules are read on every request, so a switch applies at once.
- **Changing:** labs (add, rename, renumber, remove) need `course.manage`. Rules need
  `lab.publish` in their scope: the course, or the group.
- **On the course page** (`CourseLabs`):
  - staff see each lab's state as chips (course, and any group with its own rule), a "Hapur"
    switch for the whole course, and an "Orari" panel with per-group rules, closing time and
    solutions date;
  - students see only the open labs.
  - Dates are written out in Albanian by `formatMoment`, not by Intl: not every browser
    carries Albanian locale data.

## Importing students

Built in #11. Pages: the group's students (`…/groups/:id`) and the import (`…/groups/:id/import`).

- **In the pedagog's browser:**
  - the class list is read from pasted text (Excel or Sheets columns, CSV, one name per line),
    a CSV or an `.xlsx` file (read-excel-file, loaded only for Excel);
  - each name gets a username base (`usernameBase`: first and last name, no accents) and a
    12-character password (lowercase and digits without look-alikes);
  - each password is hashed here with the same PBKDF2 code (`src/shared/password.ts`).
  - **Only hashes reach the server.** Plain passwords exist only on screen and on the printed
    slips (`CredentialSlips`: a print-only copy, A4, 10 per page, cut lines). There is no
    digital export, and the page warns before it is left unprinted.
- **On the server** (`POST …/groups/:id/students`, `student.manage`):
  - at most 25 students per request (`IMPORT_CHUNK`), and the browser sends a class in
    several requests;
  - the hash must have today's parameters (`isValidPasswordHash`);
  - usernames are numbered where taken anywhere on the platform (`arben.hoxha2`);
  - one select plus multi-row inserts of 10 rows (`ROWS_PER_INSERT`), all in one batch;
  - imported students get a group membership only.
- **Password reset** (`POST …/students/:id/password`): only for a student of that group. The
  new hash also comes from the browser, and the student's sessions end.

## Auth and sessions

Own module built from standard parts, following the Lucia / "Copenhagen Book" approach.

Built in #8: `src/api/auth/`, data access in `src/api/db/auth.ts`, routes in
`src/api/routes/auth.ts`.

- **Session token:**
  - 32 random bytes; only its SHA-256 is stored.
  - Sent as a `__Host-session` cookie: HttpOnly, Secure, SameSite=Lax, Path=/.
  - 30-day sliding expiry, renewed once less than 15 days are left, so an active session does
    not write to D1 on every request.
  - A disabled account loses its sessions at the next request. A daily cron removes expired
    sessions.
- **Passwords:**
  - PBKDF2-SHA256 through WebCrypto, 16-byte salt per hash, NFC-normalized input.
  - Stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>`. A hash with old parameters is
    replaced at the next successful sign-in.
  - 15,000 iterations. Measured in production on 2026-10-08:
    - a warm login takes 5-7 ms of CPU (failed: median 5 ms), and a cold one about 17 ms;
    - at 40,000 iterations it was 8-11 ms warm and 20 ms cold, against the 10 ms budget;
    - each 1,000 iterations cost about 0.1 ms, as on an Apple M4. Most of a login is the rest
      of the request (validation, about 5 queries, the session), so shave that first if more
      headroom is needed.
  - Cloudflare caps PBKDF2 at 100,000. Strength comes mostly from the passwords: generated ones
    are 12 or more characters from an unambiguous alphabet.
  - Check CPU time with `npx wrangler tail lab-platform --format json` (`cpuTime`) after
    changing anything on the sign-in path.
  - Unknown usernames are checked against a decoy hash, so they cost the same time as a wrong
    password, and the answer is the same.
- **CSRF:** SameSite=Lax plus an `Origin` check on every mutation (`sameOrigin` middleware).
- **Rate limiting:** failed sign-ins are counted in D1 (`login_attempts`), in fixed 15-minute
  windows:
  - 10 per username, which a correct password does not bypass;
  - 100 per IP, because a whole class shares the university's address.
  - The limits are checked before any hashing, and the answer is 429 with `Retry-After`.
- **First accounts:** `npm run account:create` (`scripts/create-account.ts`) creates an
  organization's first admin directly in D1. Everyone else is added in the app (#11).
- **Later:** email one-time codes (Resend); Google/Microsoft OAuth (Arctic); passkeys.

## Content pipeline

- **Upload:** a pedagog uploads a `.ipynb` on the lab page (**Ngarko fletore**), as the lab's
  main notebook, supplementary material or a solution (`src/web/lib/upload-notebook.ts`).
  - Their browser converts it with `renderNotebook` (`src/notebook`, #13), a TypeScript port of
    the course site's `site/scripts/notebook.mjs`. GUI cells (pygame, tkinter, subprocess,
    widgets) keep no outputs; errors, stderr and `⏳` lines are dropped.
  - The same libraries at the same versions as the site: markdown-it 15.0.2, KaTeX 0.18.7,
    `@mdit/plugin-katex` 1.1.1, Shiki 4.4.3. Shiki uses Oniguruma (WebAssembly), because its
    JavaScript engine highlights differently after Albanian letters such as "ë".
  - So the converter runs in browsers, never in the Worker, which cannot compile WebAssembly
    at run time. Its tests run in Node (the `notebook` Vitest project).
  - Load it lazily. It is about 400 KB gzipped, mostly the Oniguruma engine (232 KB).
  - **The specification:** `test/notebook/fixtures` holds the 19 course notebooks and the
    site converter's output for each (HTML as fingerprints). Every one must match.
    `scripts/snapshot-course-notebooks.ts` rewrites the snapshots from the course repo. Do it
    only on purpose.
  - **Storage** (#14), `src/api/routes/notebooks.ts`:
    - a lab has notebooks (`main`, `extra` or `solution`);
    - each notebook has files: `notebook.ipynb` (the original), `rendered.json` (the converted
      cells) and its images and figures under the converter's names;
    - files are kept in `file_chunks` of at most 512 KB, since D1 allows 2 MB per value.
  - **Gzip end to end:** the browser gzips the converted cells (up to 1.5 MB raw for the course
    notebooks, about ten times smaller gzipped) and Plotly figures before upload. The Worker
    serves them as stored, with `Content-Encoding: gzip` and `encodeBody: "manual"`, so it
    never parses or re-encodes them. It unpacks only for clients that do not accept gzip.
  - **Upload in steps** within D1's limits: `POST` the notebook, `PUT` each file (at most
    10 MB), then `POST …/ready`. Until it is ready, only staff see it.
  - **Uploaded files never run code on our origin:** only an allowlist of types is accepted
    (JSON, ipynb, PNG, JPEG, GIF, SVG). Every file is served with `nosniff` and a sandboxing
    `Content-Security-Policy`, and the original downloads as an attachment.
- **Stored rendering:** `rendered.json` is a `StoredNotebook` (`src/notebook/stored.ts`): the
  converter's result without its assets, plus `format` (1 today). Bump the format when the shape
  changes, so that older renderings can be found and converted again.
- **Display** (#14): the lab page `/o/:org/courses/:courseId/labs/:labId`, with `?notebook=` for a
  lab's other notebooks. It looks like the course site's lab page: section cards, a table of
  contents, long code folded, outputs below their code.
  - **All notebook HTML goes through `sanitize()`** (`src/web/lib/sanitize.ts`, DOMPurify) before
    it is shown. `rendered.json` is made in a browser and could be hand-crafted, so the converter's
    own escaping is not enough. Scripts, event handlers, `javascript:` links, styles, forms and
    frames are removed, and links to other sites open in a new tab. An end-to-end test uploads a
    hostile rendering and checks that it stays harmless.
  - **Embeds:** an interactive cell (Pygame, Tkinter, widgets) shows its visualization first, with
    the code folded under it. Otherwise the visualization follows the last cell made from that
    notebook cell.
  - **Images** load from the notebook's files with the reader's session. **Plotly** (4.8 MB)
    ships as its own file and loads with the first figure that comes near the screen; figures
    follow the theme. KaTeX's styles and fonts load with the lab page.
  - Solution notebooks are served only with `solution.view`, or after `solutions_from`.
  - Not yet: folding saved outputs as a spoiler. The course site did this for one homework
    notebook, whose saved chart gives the answer away. (A new version in place of a notebook is
    #208, below.)
- **Embeds** (cell → visualization + props) are stored as data: `embeds`, one per cell, from
  the 13 ids in `src/shared/visualizers.ts`, replaced as a whole with
  `PUT …/notebooks/:id/embeds`.
  - Staff edit them above the notebook. Each cell is listed by its heading, or for code by the
    section it belongs to, since a first line such as an import rarely says which exercise it is.
  - Props are typed as JSON for now; a form per visualization can come when pedagogs need it.
  - The course site's own embeds are in `test/notebook/fixtures/embeds.json`, copied by the
    snapshot script.
- **Re-render all:** an admin action that re-converts the originals when the converter improves.
- **Course import** (#16), `scripts/import-course.ts` (`npm run course:import`):
  - It reads a course site in the course repo's format: `site/content/course.mjs` (labs,
    resources, homework, embeds), the notebooks, and the solutions in `zgjidhjet/`.
  - `scripts/course-import/plan.ts` converts everything in Node; `apply.ts` uploads it through
    the API, signed in as a pedagog. So it runs the same permission checks and upload steps as the
    app, and works the same against `npm run dev` and production.
  - The plan:
    - resources become `main` or `extra` notebooks, titled without the "Laboratori N —" prefix;
    - homework becomes an `extra` notebook of its lab;
    - `X-ZGJIDHJE.ipynb` becomes the `solution` of `X.ipynb`, only if `isSolutionOf` holds, and
      takes its embeds.
  - **Sections:** a resource with `sections` (labs 5 and 6 share `laborator-05.ipynb` on the
    site) gives each lab its own `.ipynb` of whole cells (`laborator-05-laboratori-6.ipynb`).
    Each range starts at a heading that opens its cell. The embeds are renumbered for the part,
    and a rule above the part's first heading is dropped, as on the site.
  - **Re-running** (#209): it plans first, only reading, then writes.
    - A lab is matched by its number and its imported notebooks by file name.
    - A notebook whose original differs gets a new version in place (#208): same id, students' work
      moved with its cells. A new one is uploaded after the rest. Title, kind and order changes in
      the course repo are not carried over (no in-place rename yet).
    - If a new version would remove a cell where students have work, `ImportBlocked` stops it
      before any write and lists lab, file, cell and how many students; `--allow-loss` goes ahead.
    - Embeds are written when they differ, keeping a variant's pinned `seedCell`.
    - Notebooks added in the app are left alone; visibility is never touched.
  - The Node scripts run TypeScript as is, so `src/notebook/index.ts` imports its modules with
    `.ts` extensions.
  - `test/notebook/fixtures/course.json` is the site's labs and homework, written by the snapshot
    script.

## Languages

Built in #19: the interface in Albanian and English, Albanian first.

- **Messages** (`src/web/i18n`):
  - `sq.ts` is the source, plain objects grouped by screen; a message with values is a function
    (`count: (n) => …`), which also handles plurals.
  - `en.ts` is typed as `Messages`, so a missing or extra English message fails the build. No
    i18n library and no extraction step.
  - `useT()` in components (re-renders on a switch); `t()` outside React, for page titles in
    `head` and error texts. Both dictionaries ship in the main bundle (a few KB gzipped).
  - Dates are spelled from the messages' month names rather than Intl, because not every browser
    carries Albanian locale data.
  - Course content is never translated: notebooks, course, lab and group names stay as written.
- **Which language** (`useLocaleSync` in `src/web/lib/locale.ts`):
  1. the user's own choice: `users.locale`, set with `PATCH /api/me` from the account menu;
  2. else this device's choice (`localStorage.locale`), which visitors set with the header's
     toggle;
  3. else the language of the course on screen: `courses.locale`, set on the course page by
     whoever manages it, or in the new-course form;
  4. else Albanian.

  A switch updates `<html lang>` and re-runs the routes so page titles follow.
- **Tests:**
  - an end-to-end test goes through every staff screen in English, as well as the visitor's
    toggle, the account preference and a course's language;
  - it fails on Albanian letters or common Albanian interface words in visible text or
    accessible labels (course content excluded);
  - each of the 13 visualizations is opened in English and stepped once, and must contain no
    common Albanian words (place names such as Tiranë are allowed);
  - API tests cover the settings.
- **Visualizations** (`src/viz/kit/text.ts`):
  - each visualization keeps its own `TEXT = bilingual(sq, en)` beside it, so its text loads with
    its chunk rather than with every page; `useText(TEXT)` picks the interface language;
  - `bilingual()` types English against Albanian, so a missing message fails the build;
  - the algorithm modules (`algorithms/*.ts`) take their step text as a parameter, from
    `algorithms/*.text.ts`, with Albanian as the default for callers that ignore the notes;
  - pseudocode is translated word for word, keeping the lecture's structure;
  - names stay as they are: Albanian cities, people and the lab notebooks' own vertex names
    (Hidranti, Qyteti…), which students compare with their notebooks;
  - descriptive vertex names (the flowers, the house and pasta steps) get English labels; the
    flowers name the vertices outright, so the steps read in the interface language too;
  - the embed's own title comes from the course and stays as the course wrote it.

## Search

Built in #17. A ⌘K palette (also Ctrl+K, `/`, or the header's button) searches labs, notebook
sections and the visualizations as you type.

- **No FTS5:** D1 cannot export a database that has virtual tables, and the weekly encrypted
  backup is an export. The course is small (19 notebooks: about 340 sections and 150 KB of
  text), so plain rows and matching in the browser are enough. Pagefind is not used.
- **Index** (`src/notebook/search.ts`): made where a notebook is converted (the pedagog's browser,
  or the course import).
  - One section per heading: its anchor, title, plain text (math as its TeX source, KaTeX's drawn
    copy left out) and the functions and classes its code defines. Outputs are not indexed.
  - Limits are in `src/shared/search-limits.ts`: at most 400 sections of 4,000 characters.
  - Stored in `search_sections` with `PUT …/notebooks/:id/search` (staff), replaced as a whole in
    one request (41 statements at most).
  - Notebooks uploaded before #17 have no index until uploaded again. The course import rewrites
    the index of every notebook it keeps.
- **Who sees what:** `GET /api/orgs/:org/courses/:id/search` returns the labs, ready notebooks and
  sections the user may see, by the lab pages' own rules (`labContext`, `openToViewer`,
  `mayReadNotebook`).
  - Students get only labs open to their groups now, and solutions only once open; staff get
    every lab.
  - A hidden lab's text never leaves the server, so the browser searches what it receives
    without further checks.
  - API tests prove it, with the schedule, solutions and other organizations.
- **Matching** (`src/web/lib/search-text.ts`):
  - case and Albanian accents are ignored (`fold` keeps every character in place, so matches are
    marked in the original text);
  - every term must start a word;
  - a section's title weighs more than its function names, which weigh more than its text;
  - a lab whose name matches comes first.
- **Loading:** the palette is its own chunk (5 KB gzipped), loaded on first open. It fetches one
  index per current course of each of the user's organizations, cached for 5 minutes, so typing
  costs the database nothing.
- **A section result** opens the lab at `?notebook=…#anchor`. The lab page scrolls to the hash
  once the notebook has rendered, so shared links to a section work too.

## Analytics

Built in #18: weekly activity per course for staff with `analytics.view` (pedagogs, coordinators),
at `/o/:org/courses/:id/activity`, linked from the course page.

- **What counts** (`lab_activity`): a student opened a lab's notebook, downloaded its `.ipynb`,
  used one of its visualizations, or completed one of its exercises (#51; recorded when the
  completion is).
  - At most one row per student, lab, kind and day (`INSERT … ON CONFLICT DO NOTHING`), so a
    class of 120 stays at tens of thousands of rows a year.
  - Opening and downloading are recorded by the API as it serves the notebook's detail and its
    original file. A visualization is reported by the lab page (`POST …/labs/:id/activity`) on the
    first click or key inside one, once per notebook opened.
  - The writes go through `waitUntil`, after the response, so reading a lab never waits for them
    and never fails because of them.
  - Staff are never recorded.
  - Days are in `Europe/Tirane` for now (`ACTIVITY_TIME_ZONE`), and weeks run Monday to Sunday.
    A time zone per institution comes with self-service institutions.
- **The report** (`GET …/courses/:id/activity[?group=]`):
  - students of the groups the user may see: the whole course with a course-wide grant, or only
    their own groups;
  - per week, from the week the course began (at most 26 weeks): students active at all, and per
    kind;
  - per lab, since the start;
  - all as counts made in SQL (`COUNT(DISTINCT user_id)`): no student is named, and the Worker
    does not loop over rows.
- **Not yet:**
  - analytics for the institution admin (who does not see courses);
  - code runs;
  - deleting old activity (see open items in `platform-vision`).

## Slow devices and networks (#193)

`e2e/performance.spec.ts` opens Lab 4 (with its figures) as a student with the CPU slowed four times
and the network at 2 Mbit/s with 300 ms latency, and holds three budgets: the notebook readable on a
first visit (12 s), again with the cache (3.5 s), and the first cell's output with Python cached (5 s).
Measured 2026-10-30 on a laptop after #193: 6.2, 1.4 and 0.8 s (before: 8.3, 5.3 and 0.6). The local
server does not compress; production's Brotli sends the app's 877 KB as 164 KB, so production's first
visit is about 3 s faster.
It runs alone, in the `performance` Playwright project after `desktop` and `mobile`: beside other
tests on CI's few cores it measured their load (the cached reload rose from 1.8 to 5.4 s as heavy specs
were added, while a laptop still measured 1.4 s on 2026-11-01). Run it with `--project performance`.

- **`/assets/*` is immutable** (`public/_headers`, a year): the files are named by their hash. Before,
  `max-age=0, must-revalidate` made every visit re-ask for each of ~40 files, a round trip per wave
  of imports (1.6 s at 300 ms latency before the app could start).
- **The lab route's loader prefetches the notebook** (its details and `rendered.json`, the largest
  download) with the lab's other queries, for `?notebook=` or the first finished notebook, instead of
  after the page has rendered.
- **No Zod in the app:** value imports from schema files had pulled Zod (87 KB) into the lab route.
  Values the app needs live in schema-free files (`kolokium.ts`, `code-limits.ts`, `staff-roles.ts`,
  like `exercise-limits.ts`), and `test/scripts/no-zod-in-app.test.ts` follows every value import of
  `src/web` and `src/viz` into `src/shared` and fails on any that reaches Zod.
- Python starts while the student reads, so a cell runs at once with the engine cached (#191).

## Accessibility (#192)

Target: WCAG 2.2 level AA, which public institutions are asked for and which every student needs.

- **Checked by tests:** `e2e/accessibility.spec.ts` runs axe (`@axe-core/playwright`, tags `wcag2a`
  to `wcag22aa`) on 20 pages (visitors, students and staff, including the lab page, submissions,
  reports and the student import) on desktop and the 375 px phone, in the light and the dark theme.
  Any violation fails the build, listed with the element and, for contrast, the ratio.
- **Keyboard:** the same file walks a lab with the keyboard alone: Tab reaches a cell's Run and
  Enter runs it, Enter opens the code editor, Escape then Tab leaves it (CodeMirror's
  `indentWithTab` keeps Tab for indenting; no trap, 2.1.2), and handing in with its confirmation.
- **Rules the first audit taught (2026-10-29):**
  - Contrast 4.5:1 for text (1.4.3). HeroUI's success and warning are fills, too pale as text (2.2
    and 2.0): `--success` and `--warning` are darker in the light theme, and `--accent-soft` is an
    opaque 10% tint so accent text on it reaches 4.7. GitHub's light code colours below 4.5 on the
    code background (red, orange, green, comments) are a shade darker in the same hue, in Shiki's
    output (by their inline colour) and in the editor alike.
  - A control's name contains its visible text, first (2.5.3, for voice control): the logo is
    "Lab Platform – Kreu", the language button "EN – …", the account button is named by its content
    (initials, a space, the name; the name is `sr-only` on phones). axe judges by what is visible,
    so `aria-hidden` on visible text does not help: text that is not the name goes outside the
    control (the live graph's badges are a layer of their own).
  - A region that scrolls sideways must be reachable by keyboard (2.1.1): wide tables sit in
    `ScrollRegion` (a named, focusable `section`). Code and output blocks rely on browsers making
    scrollers focusable (Chrome, Firefox) and on touch.

## Design system (#128)

- **Tokens** live in `src/web/styles.css`. The algorithm states (`--state-frontier`, `-current`,
  `-visited`, `-path`, `-done`, `-reject`, `-unvisited`) mean the same everywhere; the visualization
  kit's `--viz-*` names point at them, and Tailwind exposes them as `bg-state-*` / `text-state-*`.
  Every state also has a shape or a label, never colour alone.
- **Type:** Bricolage Grotesque (headings, `--font-display`), Inter (text), JetBrains Mono (code),
  all self-hosted through Fontsource because the app is cross-origin isolated.
- **Motion:** Motion for React through `src/web/lib/motion.tsx` only: `MotionProvider` (LazyMotion,
  strict, so components use `m.*`; the features chunk loads after the page) and the named springs
  in `SPRING`. `MotionConfig reducedMotion="user"` and a CSS rule stop all movement for users who
  ask for reduced motion.
- **Budget:** the app shell (the `index` chunk) stays near 120 kB gzipped; measure it in any PR
  that adds a dependency to it.

## Quality, deploy, backups

- **Tests:**
  - Vitest in the Workers runtime: API, permissions, tenant isolation.
  - Playwright end-to-end, porting the ideas from `site/scripts/qa.mjs`. The course is imported
    from the fixtures with the import's own code, which must give the site's labs, change nothing
    when run again, and keep hidden labs and solutions from students. Every one of the 19 course
    notebooks must then show each visualization,
    without errors or overflow at 375px, even with every letter 0.25px wider (text renders a
    little wider on CI's Linux than on a Mac); each visualization opens and steps; a pedagog's
    upload, embed editing and deletion run through the real UI.
  - Biome for lint and format.
- **CI/CD:**
  - On every PR, GitHub Actions runs lint, typecheck, the migration and route-tree checks,
    tests, the build and the end-to-end tests.
  - On `main`, once all of that passes, it applies the D1 migrations (`--remote`), deploys
    (`npm run deploy`) and checks `/api/health` on the live site. Runs on `main` are never
    cancelled midway.
  - Migrations run before the new code goes live, so they must be additive: never rename or
    drop what the running code still uses in the same release.
  - The GitHub token (Workers Editor, D1 Write, Workers Observability Write, Account Settings
    Read) can deploy and migrate, but cannot create or delete Workers. A new Worker needs one
    deploy with the owner's `wrangler login`.
  - Live at https://lab-platform.florjanimema.workers.dev until the product has a domain.
  - Later: preview versions for branches.
- **Data location:** the production D1 database was created with the EU jurisdiction, so it is
  stored and processed only in the EU. This cannot be changed after creation.
  Live Lab Durable Objects use the EU jurisdiction too (`LIVE_JURISDICTION` "eu"; local runtimes
  cannot, so dev, tests and e2e set "none") and delete their storage when a class ends. Workers
  AI has no EU restriction: its requests carry no names, and the DPA and privacy page say so.
- **Backups:**
  - D1 Time Travel: restore to any minute of the last 7 days (30 on the paid plan).
  - Weekly (`.github/workflows/backup.yml`): `wrangler d1 export`, encrypted with the owner's
    age key before upload, kept 90 days as a private workflow artifact. GitHub never sees the
    plaintext. Never commit an export: it contains student data.
  - **A raw export does not import (#181).** It writes every index after all rows, but our foreign
    keys point at (id, org_id), so SQLite needs the parent's unique index first ("foreign key
    mismatch"); and file chunks (512 KB, as hex) exceed D1's 100 KB per statement ("statement too
    long"). `scripts/restore-backup.ts` prepares it: tables, then indexes, then rows, and each long
    value in pieces put back with `unhex(group_concat(… ORDER BY k))` (both work in production D1).
  - **The drill:** `npm run backup:restore` restores the latest backup locally, applies newer
    migrations, and checks tables, `PRAGMA quick_check` (D1 refuses `integrity_check`),
    `foreign_key_check`, complete files and renderings, and the app opening a course as a throwaway
    coordinator. Counts only; the plaintext lives in a private temporary folder and is deleted. First
    run, 2026-10-27, on the 2026-10-26 backup: restores, every check passes.
- **Usage meter (#180):** `scripts/usage.ts` (`npm run usage`) reads today's (UTC) Worker requests
  (`workersInvocationsAdaptive`) and D1 rows read and written (`d1AnalyticsAdaptiveGroups`) from the
  GraphQL Analytics API for the whole account, since the limits are per account, and compares them
  with the free plan's. The Usage workflow runs it at 07, 11, 15 and 19 UTC and fails from 70%, so
  GitHub emails the owner; it needs `CLOUDFLARE_ANALYTICS_TOKEN` (only "Account Analytics: Read",
  apart from the deploy token) and warns without it. Analytics are kept 31 days.
- **Observability:** Workers Logs (free: 200,000 events a day, kept 3 days).
  - **Browser errors (#179):** `src/web/lib/report-error.ts` reports uncaught errors, rejections and
    what the error boundaries catch (not API failures, which the server logs) to
    `POST /api/client-errors`: the page as its route id, the message with ids masked, the place in the
    app's own code, the build (its script's name). At most 10 a page load, each message once. The
    server logs each as one `{"type":"client_error", …}` line with the browser's name, at most 60 a
    minute per isolate, and records no user.
  - `npm run errors` follows them live with `wrangler tail` (the owner's login has `workers_tail`, not
    observability read) and prints browser errors and the server's exceptions and error logs, never a
    request's address, IP or headers; the last 3 days are in the dashboard (Observability, filter
    `type = client_error`). A third-party service such as Sentry is not needed for now.

## Portability

- Hono runs on Node, Bun and Deno.
- Drizzle supports Postgres.
- Keep Cloudflare-specific code (D1, Durable Objects, AI, assets) behind small adapters, so
  leaving Cloudflare is a port, not a rewrite.

## Privacy

- **Minimal personal data:** full name, username, optional email.
- **Learning activity** is kept per student and day only to count distinct students. Reports show
  counts, never names, and no third-party tracker is used.
- **Retention (#116):** `src/shared/retention.ts` is the one list of periods. The daily cron
  (`applyRetention`) deletes what passed them, at most `RETENTION_BATCH` rows per table a run to stay
  within D1's daily writes; the privacy page prints the same numbers.
- **Institutions own their data:** the admin downloads it all (#117, `src/shared/org-export.ts`:
  paged parts assembled in the browser) and erases people on request (#115).
- **Data sent to AI:** only the question and the code or output context, never names.
- **Data processing agreement:** `docs/legal/dpa-template.{sq,en}.md`, under Law No. 124/2024.
  Its annexes (security measures, sub-processors, retention) describe the code, so a change to
  any of them updates the template in the same PR.
